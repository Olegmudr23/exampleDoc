# Календарь приёмов и кабинет специалиста

Проект календаря для одного специалиста: запись на приём, карточки пациентов, учёт процедур, вложений и расчётных показателей. Я формировал требования и документацию, на основе которых создавалось приложение для решения практических задач и личного изучения технологий.

[Все примеры](../../README.md) · [Карточка пациента и вложения](patient-card.md) · [Исследование интеграции переписки](messaging-research.md)

Описание подготовлено по README, исходному коду и проектным заметкам. Рабочая база, персональные записи, параметры сервера и учётные данные в подборку не включены.

## Архитектура и границы

- Клиент — HTML, CSS и JavaScript; сервер — Node.js; хранение — SQLite.
- Один специалист, одно расписание и общий пароль кабинета. Ролевой модели нет.
- Приёмы и карточки сохраняются на сервере и переживают перезапуск.
- Серверные сессии действуют 12 часов и хранятся в памяти; после перезапуска требуется вход.
- При одновременном изменении одного приёма сохраняется последнее изменение. Механизм из [учебной схемы блокировок](../concurrency/) в этом приложении не реализован.

## Основные сущности

| Сущность | Назначение и связи |
| --- | --- |
| Пациент | Контактные данные, дата рождения, аллергии и заметки; связан с приёмами, анамнезом, этапами лечения и вложениями |
| Приём | Дата, время, длительность, статус, категория, процедуры, импланты и примечания; относится к пациенту |
| Процедура | Название, категория, длительность, цена, себестоимость и признак установки импланта |
| Система импланта | Справочник для выбора при выполнении процедуры |
| Установленный имплант | Связан с завершённым приёмом; содержит систему, серийный номер и параметры установки |
| Этап лечения | Самостоятельный элемент плана пациента; изменение его статуса не завершает приём |
| Вложение | Файл, метаданные и содержимое в SQLite; связано с пациентом |

## Правила календаря и карточки

1. Предусмотрены представления дня, недели и месяца. Интервалы можно создавать с шагом 15 минут.
2. Пересекающиеся приёмы разрешены и отображаются в отдельных полосах.
3. Статусы приёма: «Запланирован», «Подтверждён», «Завершён», «Отменён».
4. Телефон пациента обязателен; дата рождения может быть заполнена позже. Если она указана, уникальна пара «нормализованный телефон + дата рождения».
5. При завершении установки имплантов требуется заполнить серийные номера и параметры. Серийные номера проверяются на уникальность без учёта регистра.
6. Этапы лечения имеют статусы «Запланирован», «В работе», «Выполнен», «Отменён» и ведутся отдельно от фактических процедур приёма.

## Правила расчётов

`Прямые затраты = Σ(количество процедур × себестоимость) + Σ(закупочные цены имплантов) + дополнительные материалы`.

`Расчётная маржа = стоимость процедур − прямые затраты`.

Незаполненная цена хранится как `null`, бесплатная процедура — как `0`. Если хотя бы одна цена процедуры в приёме не заполнена, стоимость и маржа приёма неизвестны. Приём исключается из соответствующих сумм частной практики, а расходы остаются в общих затратах. Запланированные и отменённые приёмы не входят в фактические показатели. Маржа не является фактом оплаты или бухгалтерской прибылью.

## Вложения и резервные копии

Разрешены PDF, DOC, DOCX, JPG, PNG и UTF-8 TXT размером до 5 × 1024 × 1024 байт. Сервер проверяет размер, расширение и базовую сигнатуру файла. Предпросмотр предусмотрен для PDF, JPG, PNG и TXT; Word скачивается.

SQLite хранит содержимое файлов вместе с данными карточки. Согласованная резервная копия создаётся через SQLite Online Backup API. Удаление текущего вложения не удаляет его из ранее созданных копий.

## Проработанная интеграция

В проекте есть отдельная исследовательская заметка по переписке через Bot API MAX: приём webhook, идемпотентное сохранение сообщений, связь с карточкой пациента и собственный счётчик непрочитанных. Это предложение архитектуры, а не действующая функция. Заметка вынесена в [отдельный документ](messaging-research.md) с исходной датой исследования.
