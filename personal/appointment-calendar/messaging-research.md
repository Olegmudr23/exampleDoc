# Исследование интеграции переписки через MAX

Архивный исследовательский материал из личного проекта. Исходная проверка источников датирована 13 ноября 2026 года; при подготовке подборки актуальность внешнего API не перепроверялась. Интеграция не реализована.

Проверено по официальной документации 13 ноября 2026 года. Это исследование и предложение архитектуры; подключение к MAX и изменение приложения не выполнялись.

## Доступные пути

### Bot API — рабочий вариант для переписки с ботом клиники

Пациент начинает общение с ботом, а приложение получает входящие события `message_created` и может отправлять ответы через `POST /messages`. Ответы идут от имени бота. Бот не подключается к существующему личному диалогу врача с пациентом. Источник: [разработка сценариев бота](https://dev.max.ru/docs/chatbots/bots-coding/prepare/), [отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages).

Нужны верифицированный профиль российской организации, ИП или самозанятого, создание бота, модерация и токен. Обычному физическому лицу создание бота сейчас недоступно. Источники: [подключение к платформе](https://dev.max.ru/docs/maxbusiness/connection/), [создание бота](https://dev.max.ru/docs/chatbots/bots-create/create/).

Для production требуется Webhook: публичный HTTPS endpoint на порту 443, сертификат доверенного центра, проверка секрета `X-Max-Bot-Api-Secret`. Обновления нужно принимать и подтверждать в пределах 30 секунд. Long Polling документация оставляет для разработки и тестирования. Источник: [POST /subscriptions](https://dev.max.ru/docs-api/methods/POST/subscriptions).

Текущий адрес API — `https://platform-api2.max.ru`; авторизация — заголовок `Authorization: <token>`. Документация также требует доверия к сертификатам Минцифры. Токен должен оставаться на сервере, а доверенные сертификаты настраиваются без отключения проверки TLS. Источник: [обзор API](https://dev.max.ru/docs-api).

### Open Client API — отдельная программа, не готовый серверный коннектор

MAX предлагает API альтернативных клиентов. Требуются одобрение приложения, сертификат участника и App-ID; полные методы предоставляются участникам. Публичные условия предусматривают прямое соединение с устройства пользователя, запрещают серверное посредничество, передачу полученных данных на сервер разработчика и объединение с другими источниками. Поэтому стандартный серверный импорт личных переписок в нашу SQLite-базу не соответствует опубликованной модели. Для иного варианта нужно отдельно согласовать сценарий с MAX; доступ и конкретные методы заранее не гарантированы. Источники: [описание](https://dev.max.ru/docs/open-api/), [условия Open Client API](https://legal.max.ru/openclient-docs).

## Предложение для нашего приложения

Предлагаемая первая версия при выборе Bot API:

1. Раздел «Сообщения»: список диалогов, последнее сообщение, время, поиск, фильтр непрочитанных и общий значок со счётчиком.
2. Лента переписки и поле ответа от имени бота. На первом этапе — текст; файлы и медиа потребуют отдельной обработки вложений.
3. Привязка диалога к карточке пациента, переход из переписки в карточку и создание приёма для выбранного пациента.
4. Собственный признак прочтения в кабинете. Новое входящее сообщение увеличивает счётчик, просмотренные сообщения помечаются прочитанными. Это не обещание синхронизации со статусом прочтения в официальном клиенте MAX: в опубликованном перечне Bot API событий прочтения не обнаружено. Источник для проверки: [объект Update](https://dev.max.ru/docs-api/objects/Update/).

Связывать пациента только по имени нельзя. В стандартном объекте User телефон не указан; его можно запросить отдельной кнопкой `request_contact`, либо связать диалог вручную. Поскольку у нас уникальна пара «телефон + дата рождения», один телефон тоже не гарантирует единственного пациента. Первую версию лучше сделать с выбором пациента врачом и подтверждением связи. Источники: [User](https://dev.max.ru/docs-api/objects/User/), [кнопки запроса контакта](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard/).

Историю нужно накапливать из доставленных событий с момента подключения. Нельзя обещать импорт всех прежних переписок: `GET /messages` по chat_id документирован для групп / каналов, где бот является администратором, а не как универсальная выгрузка личного аккаунта. Источник: [получение сообщений](https://dev.max.ru/docs-api/methods/GET/messages).

## Изменения сервера, которые потребуются

Это предложения реализации, а не уже добавленные возможности:

- Отдельный входящий маршрут, например `/integrations/max/webhook`. Он не должен требовать браузерной сессии или Origin браузера; вместо этого нужна проверка webhook-секрета и ограничения тела запроса. Остальные API сохраняют существующую авторизацию.
- Таблицы диалогов, сообщений, связи с пациентом и состояния прочтения в SQLite. Поля идентичности MAX хранить без потери точности int64; не полагаться на безопасную точность JavaScript Number для любых внешних идентификаторов.
- Идемпотентное сохранение по идентификаторам сообщения / события, чтобы повторная доставка не удваивала непрочитанные. Обработка редактирования и удаления, включая запоздавшие события.
- Подтверждать событие только после надёжного сохранения. Вызовы отправки и тяжёлая обработка должны выполняться отдельно от быстрого приёма webhook.
- Счётчик по собственному порядковому номеру входящих сообщений и границе последнего просмотра. При отметке прочитанного фиксировать только действительно показанную границу, чтобы новое сообщение не потерялось из счётчика из-за гонки.
- Обновление интерфейса через SSE или периодический запрос. MAX продолжает присылать webhook, даже когда кабинет в браузере закрыт, если наш сервер доступен.
- Секреты в переменных окружения, например `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`. Не включать тексты сообщений и токены в обычные логи.

Для приложения после размещения публичный endpoint можно обслуживать через подготовленный Caddy HTTPS-прокси после размещения на сервере. Один localhost без публичного HTTPS endpoint не примет production-webhook MAX.

Перед реальным использованием нужно определить правила доступа, хранения и удаления переписки пациентов вместе с клиникой. Эта заметка не подтверждает соответствие медицинской информационной системы каким-либо требованиям.

## Что выяснить перед реализацией

Главное: пациенты должны продолжать писать в личный аккаунт врача или готовы писать боту клиники? Для первого сценария Bot API не решает задачу. Для второго можно реализовать описанный модуль после выбора владельца бота и получения доступа к платформе. Токен не нужно присылать в переписку — его следует настроить на сервере.
